# Сохранение сессии в astra-vault

Задача: превратить сделанную работу в заметки, по которым через три месяца
можно восстановить не только *что* сделано, но и *почему именно так*.

Хранилище: `astra-vault/` (в корне репозитория). Язык заметок — русский.
**Ничего не коммитить** — `git add`, `git commit`, `git push` не запускать,
историю формирует пользователь сам.

## Порядок

1. **Собрать факты.** Что уже известно из текущей сессии — использовать как
   есть, не перевыводить из кода. Добрать недостающее:

   ```
   git log --oneline <первый коммит сессии>~1..HEAD
   git status --short
   ```

   Хеши коммитов, номера миграций Alembic (`alembic/versions/`), число тестов
   — только настоящие. Число тестов брать из вывода `pytest`/`make test`, если
   он был в этой сессии; **не было прогона — числа не писать**.

2. **Прочитать, куда пишем**, если ещё не читали в этой сессии:
   `00-home/текущие приоритеты.md` и одну свежую заметку из `sessions/` —
   чтобы попасть в тон и в структуру, а не изобретать свою.

3. **Написать заметку сессии** в `sessions/` (см. формат ниже).

4. **Разложить знание по типам.** Не всё скопом в сессию: сессия — это
   хроника, а `knowledge/` — то, что переживёт сессию.

   | Что случилось | Куда |
   |---|---|
   | Выбрали одно решение из нескольких, есть отброшенная альтернатива | `knowledge/decisions/` |
   | Разобрали баг, причина оказалась не там, где симптом | `knowledge/debugging/` |
   | Приём, который будем повторять в других модулях | `knowledge/patterns/` |
   | Цифры, деньги, оценка идей | `knowledge/business/` |
   | Как устроена интеграция со внешним сервисом | `knowledge/integrations/` |
   | Архитектура, которая меняется редко | `atlas/` |

   Одна заметка = одно утверждение. Мелкая правка без развилки — просто
   строка в заметке сессии, отдельный файл не нужен.

5. **Обновить `00-home/текущие приоритеты.md`.** Это главный файл: с него
   начинается следующая сессия. Что сделать:
   - перенести закрытое из «Осталось» — либо убрать, либо переписать как
     сделанное в «Ранее в фокусе»;
   - обновить блок «В фокусе» под то, чем занимались;
   - в «Осталось» дописать всё, что осталось несделанным, **с конкретикой**:
     номер миграции, переменная окружения, что именно проверить руками;
   - поднять `date:` во фронтматтере на сегодняшнюю дату.

6. **Обновить `00-home/index.md`** — дописать новые заметки в нужные списки
   («Решения», «Паттерны», «Отладка», «Сессии») и поднять `date:`. Заметка,
   которой нет в index, для следующей сессии не существует.

7. **Отчитаться пользователю**: какие файлы созданы, какие изменены, и что
   осталось в «Осталось» — коротким списком. Не пересказывать содержание
   заметок целиком.

## Формат заметки сессии

Имя файла: `YYYY-MM-DD краткое утверждение.md` — о чём была сессия, а не
«сессия 12». Например: `2026-07-29 админ-панель разделы метрики очередь и
рассылки.md`.

```markdown
---
tags: [session, <2–4 тега: модуль, тема — по-русски или латиницей как в vault>]
date: YYYY-MM-DD
---

# Заголовок с сюжетом, а не «Итоги сессии»

Абзац-завязка: с какого вопроса начали и чем кончилось. Здесь же цифры —
сколько коммитов, тестов, какие миграции.

## Что собрали

- **Название куска** (`хеш`) — что теперь работает и какую дыру закрывает.

## Развилки, снятые с заказчиком

- **Выбор.** Что рассматривали, что перевесило и чем заплатили.
  См. [[заметка из decisions]].

## Разобранные баги

- [[заметка из debugging]]

## Открыто

- Что не сделано и почему — конкретно, чтобы можно было взять и продолжить.
```

Разделы — по факту. Не было развилок — раздела нет; пустых заголовков
не оставлять.

## Формат заметок knowledge/

Общее: фронтматтер `tags` + `date`, первый тег — тип (`decision`,
`debugging`, `pattern`), H1 повторяет утверждение из имени файла, в конце —
wiki-ссылки на связанные заметки. Строки до 79 знаков, проза, не бюллетени
ради бюллетеней.

**`decisions/`** — H1 = само решение утверждением. Дальше: **Почему**
(перечислением причин), **Цена решения** — чем заплатили, **Когда
вернёмся** — при каком условии решение пересматриваем. Отброшенную
альтернативу называть прямо: «Cloudflare Tunnel рассматривали и отклонили».

**`debugging/`** — H1 = баг утверждением в прошедшем времени («стрики росли
только от повторного /start»). Сначала как выглядел симптом и в чём
оказалась настоящая причина, потом **Как починили**, потом **Урок** — что
проверять в следующий раз, чтобы не повторилось.

**`patterns/`** — H1 = приём утверждением. Короткий фрагмент кода, потом
**Почему так**, потом **Что важно не забыть** — грабли, которые не видны из
кода. В конце — где ещё этот приём применим.

## Имена файлов

Имя = утверждение, не категория. Агент видит имя **до** содержимого, поэтому
по нему должно быть понятно, надо ли открывать.

| Плохо | Хорошо |
|---|---|
| `bugs.md` | `стрики росли только от повторного start.md` |
| `админка.md` | `Tailscale вместо публичного домена для админ-панели.md` |
| `рефакторинг.md` | `фильтры аудитории как подзапросы по id.md` |

Кириллица в именах, пробелы вместо дефисов, без даты (кроме `sessions/` и
разовых отчётов вида `оценка идей монетизации Astra 2026-06-13`).

## Чего не делать

- Не писать заметку, которая пересказывает диф. Диф есть в git; в vault
  идёт то, чего в коде не видно, — почему выбрали так и чем заплатили.
- Не заводить файл на каждую мелочь: пять заметок по одной строке хуже одной
  внятной.
- Не выдумывать числа тестов, хеши и проверки, которых не было.
- Не оставлять «Открыто: доделать» — непонятно, что именно доделать.
- Не переписывать «текущие приоритеты» с нуля: файл накопительный, старые
  треки переезжают в «Ранее в фокусе» и «Треки на паузе», а не исчезают.
- Не коммитить.
