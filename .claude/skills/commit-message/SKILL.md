# Сообщение коммита для Astra

Задача: посмотреть, что изменилось, и выдать **готовый текст** сообщения
коммита. **Не запускать `git add`, `git commit`, `git push`** — что и когда
попадает в историю, решает пользователь.

## Что сделать

1. Собрать картину изменений:

   ```
   git status --short
   git diff --stat HEAD
   git diff HEAD
   ```

   Новые файлы в `git diff HEAD` не попадают — прочитать их отдельно
   (`git status --short` покажет их как `??`).

   Если пользователь передал аргумент (`/commit-message staged`, имя файла,
   диапазон) — ограничиться этим срезом. Без аргумента брать всё
   незакоммиченное.

2. Если изменений нет — сказать об этом и остановиться. Если правки
   распадаются на два-три несвязанных куска (например, фича + попутный
   рефакторинг чужого модуля) — предложить разбить на коммиты и дать
   сообщение на каждый, указав, какие файлы в какой.

3. Не пересказывать diff построчно. Понять **зачем** сделана правка: какую
   проблему человека или системы она закрывает. Если это выяснялось в текущей
   сессии — использовать то, что уже известно, а не перевыводить из кода.

4. Выдать текст (см. формат) в одном фенсед-блоке без языка, чтобы его можно
   было скопировать целиком. Ниже — команда с Run-кнопкой, чтобы пользователь
   мог закоммитить одним нажатием, если захочет:

   ```bash
   git commit -F - <<'EOF'
   <текст>
   EOF
   ```

   Файлы в индекс не добавлять и в команду `git add` не вставлять — пусть
   пользователь сам решит, что попадёт в коммит.

## Формат

```
тип(область): суть одной строкой

Абзац прозой: что теперь происходит и почему так.

Второй абзац: решения, компромиссы, неочевидные места.

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

**Заголовок:** ≤ 72 знака, тип латиницей, область и суть по-русски, после
двоеточия строчная буква, точки в конце нет. Типы в ходу: `feat`, `fix`, `ui`,
`docs`, `refactor`, `test`, `chore`. Области — по-русски и по продукту, как в
истории: `профиль`, `рассылки`, `логи`, `админ-панель`, `метрики`, `аналитика`,
`таро`, `vault`.

**Тело:** русская проза, абзацы через пустую строку, строки до 76 знаков.
Списков-бюллетеней в истории нет — не начинать. Пишем как объяснение коллеге:
сначала что человек теперь видит, потом почему сделано именно так.

Обязательно упомянуть, если есть:

- номер миграции Alembic и что она накатывает;
- новую переменную окружения или ручной шаг после деплоя;
- принятый компромисс и отброшенную альтернативу («скользящих окон нет
  намеренно — их нельзя сравнить с прошлым месяцем»);
- на чём проверено (живая база, реальный аккаунт, число тестов), если
  проверялось.

Трейлер `Co-Authored-By` ставить, только если правку делал я. Если пользователь
писал код сам — убрать.

## Чего не делать

- Не писать «обновлены файлы», «различные улучшения», «рефакторинг кода» —
  такой заголовок не несёт информации.
- Не перечислять имена файлов и функций вместо смысла. Имя модуля уместно, когда
  без него не объяснить решение (`users_crud.clear_birth_time`).
- Не выдумывать проверку, которой не было.
- Не добавлять ссылки на задачи и PR — в истории Astra их нет.

## Пример из истории

```
ui(логи): уровень заглавными и полная дата в каждой строке

Уровень был «info» строчными и терялся в строке — теперь INFO, WARN, ERROR
одной ширины: по нему скользят глазами первым делом. Время показывалось без
даты, а логи смотрят через `docker compose logs` сразу за несколько суток, и
«11:46» заставляло гадать, вчера это было или на прошлой неделе.

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```
