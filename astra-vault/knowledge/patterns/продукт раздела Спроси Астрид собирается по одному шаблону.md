# Продукт раздела «Спроси Астрид» собирается по одному шаблону

Раздел «✨ Спроси Астрид» — готовые вопросы к своей натальной карте, каждый
вопрос = отдельный товар. Первый собранный продукт — «Сколько судьбоносных
партнёров?» ([[сколько судьбоносных партнёров считает Python а объясняет LLM]]).
Остальные вопросы делаются по этому же шаблону, ничего не изобретая заново.

## Главный принцип

**Числа и факты считает Python, LLM их только объясняет.**

Причина не в красоте архитектуры: карта одна, значит ответ должен быть один.
Если цифру придумывает модель, на повторной покупке она выдаст другую — и
доверие к продукту закончится в тот же день. Поэтому:

- расчёт детерминированный, с версией метода (`METHODOLOGY_VERSION`);
- снимок расчёта кладётся в БД вместе с ответом;
- в схеме ответа LLM **нет ни одного числового поля**, которое модель могла бы
  «прикинуть» — посчитанное подставляет код при рендере.

## Порядок работ на новый вопрос (не переставлять)

1. **Формулировка кнопки** — вопрос со знаком «?», от первого лица,
   кликбейтно. Утверждает пользователь, до кода.
2. **Метод расчёта** — какие факторы карты отвечают на этот вопрос, какие веса,
   какие пороги. Утверждается устно, потом код.
3. **Проверка распределения** — счёт на ~200–300 случайных карт, квантили,
   правка порогов под целевое распределение. До промпта.
4. **Калибровки** — возраст, статус, «что делаем без времени рождения».
5. **Промпт** — черновик и обсуждение по-русски, утверждение,
   **перевод на английский** и только потом в код (значения полей — кириллицей).
6. **Схема ответа + `validate()`** — без числовых полей: числа подставляет код.
7. **Товар в каталоге** — миграция, цена в `product_prices`.
8. **Роутинг вопроса** в `handlers/ask_astrid.py` вместо заглушки.
9. **Карточка/шаринг** — если у продукта есть «одно главное число».
10. **Тесты** — правила расчёта, границы, флоу покупки (включая скидку 100%).
11. **Живой прогон промпта** на реальной карте, глазами.
12. **Миграция и E2E на проде.**

## Что делается на каждый новый вопрос

| Шаг | Файл | Что там |
|-----|------|---------|
| 1. Расчёт | `src/astra/ask/<вопрос>.py` | правила → факты, числа, `notes` для промпта |
| 2. Схемы | `src/astra/ask/schemas.py` | `*Result` — воспроизводимый снимок расчёта |
| 3. Промпт | `src/astra/llm/prompts/ask/<вопрос>.py` | схема ответа, `validate`, `render_answer`, `card_caption` |
| 4. Товар | миграция | `products` + `product_prices` (цена правится в БД) |
| 5. Кнопка | `src/astra/telegram/ask_text.py` | вопрос уже есть в `ASK_QUESTIONS` |
| 6. Роутинг | `handlers/ask_astrid.py` | ключ вопроса → платный флоу вместо заглушки |

Общее — уже написано и переиспользуется: `ask_readings` (одна таблица на все
вопросы), `ask/windows.py` (транзитные окна), `llm/prompts/ask/base.py`
(персона, парсинг JSON, стоп-фразы), `ask_keyboards.py`, worker-хендлер
`handle_ask_answer_generate`, авто-refund.

## Флоу покупки (одинаков для всех вопросов)

```
вопрос → архив? отдать бесплатно
       → нет времени рождения? предложить вписать (не запирать)
       → один калибрующий вопрос человеку
       → инвойс → оплата
       → расчёт синхронно (десятки мс) → карточка уходит СРАЗУ
       → задача в RabbitMQ → worker пишет разбор → доставка
       → разбор не собрался → авто-refund + честное сообщение
```

Карточка до разбора — не украшение: она закрывает 10–40 секунд ожидания LLM и
превращает паузу в саспенс. Плюс её пересылают друзьям (реф-ссылка в кнопке).

## Нюансы, которые дорого узнавать заново

- **Калибровка возрастом.** Без потолка «сколько уже было» по возрасту транзитные
  окна выдают 3–4 истории двадцатипятилетнему. Потолок: до 22 — одна, до 28 —
  две, до 35 — три.
- **Деление по доле прожитых окон, а не по их числу.** Иначе у человека за сорок
  всё всегда оказывается позади, и половина продукта («сколько впереди») мертва.
- **Спрашивать только то, что нельзя посчитать.** Текущий статус — спрашиваем
  (он не в карте). «Сколько было» — никогда: угадывание прошлого и есть вау-эффект.
- **Пороги — по распределению, а не на глаз.** Считаем счёт на выборке из
  ~200 случайных карт, смотрим квантили, ставим границы. Целевое распределение
  задаётся заранее (у партнёров: 15/35/30/15 на 1/2/3/4).
- **Без времени рождения не запираем.** Считаем по Венере и её аспектам, дома не
  упоминаем вовсе, в конце ответа честная приписка. Заодно это лучший момент
  дозаполнить профиль — выигрывают все продукты.
- **Вопросы про другого человека сюда не берём.** «Что он чувствует?», «Есть ли
  у нас будущее?» — по своей карте на них честно не ответить, нужна его дата
  рождения. Это воронка в «💕 Совместимость», а не вопрос раздела.
- **Эфемериды.** Транзиты считаем через `swisseph` с флагом `FLG_MOSEPH` —
  файлы эфемерид не нужны. Астероиды (Юнона, Даракарака и прочая экзотика) в
  Moshier недоступны — метод строим без них.
- **Джйотиш не мешаем с западной картой.** Один продукт — одна система координат.
- **Промпт в коде — на английском.** Обсуждаем и утверждаем по-русски, в
  репозиторий кладём перевод; внутри промпта правило «значения полей — по-русски».
  Правило проекта, см. `CLAUDE.md` → Конвенции кода.
- **Скидка 100% ≠ бесплатный инвойс.** Telegram не принимает инвойс на 0 звёзд:
  при `discount_percent = 100` товар выдаётся сразу, минуя оплату.

## Проверка качества перед релизом

1. Распределение чисел на выборке карт — не должно быть перекоса в один ответ.
2. Живой прогон промпта на реальной карте: модель обязана называть факторы
   («Сатурн шёл по твоему десценденту в 31 год»), а не «звёзды говорят».
3. `validate()` ловит: несовпадение количества блоков с числом, короткие
   портреты, стоп-фразы. Не прошло — retry, три попытки, потом refund.
