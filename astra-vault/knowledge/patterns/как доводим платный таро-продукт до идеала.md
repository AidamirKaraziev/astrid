# Как доводим платный таро-продукт до идеала

Краткая инструкция — суть подхода к раскладам (и любому LLM-продукту с
предсказуемым выводом). Проверено на «Да/Нет», «Три карты», «Отношения».

## Принципы

1. **Один расклад = один продукт.** Своя Pydantic-схема, свой промпт, свой
   формат сообщения. Общее (персона Астрид, согласование рода) — в `base.py`,
   не дублируем. Разное — раздельно.
2. **Вывод LLM — структурированный JSON: поле на позицию.** Никогда не парсим
   абзацы вслепую. Тогда позиция↔текст детерминированы, съехать нельзя, а
   вердикт/вступление — отдельные поля, а не «угадай абзац».
3. **Рендер из полей на этапе генерации.** Финальное HTML-сообщение собираем по
   жёсткому шаблону и храним готовым; доставка просто шлёт его.
4. **Творческие развилки — 2–3 варианта с превью, выбирает пользователь.**
   (фреймворк расклада, названия, тон). Не угадываем молча.
5. **Чиним корень, изолированно.** Не переиспользуем чужую постобработку
   (`sanitize` прогноза сломал расклады). Общий код не трогаем без нужды —
   чтобы не задеть другие продукты.
6. **Тестируем весь путь** parse → validate → render на реалистичных выводах
   модели, а не куски по отдельности (именно этот пробел пропустил баг).
7. **Промпт можно на английском** (дешевле токены), но вывод — строго русский:
   явное правило `VALUES IN RUSSIAN` + русские ключи данных + русская PERSONA.
8. **Валидация ловит пустые/куцые поля и вердикт.** Провал → расклад `failed`,
   дневная попытка возвращается, пользователю — тёплый fallback.
9. **Финальная проверка — на живом прогоне** (`make worker` → расклад в TG).
   Текст — поведение модели, а не кода; тесты гарантируют структуру, не слова.

## Рабочий цикл одной правки

собрать контекст → предложить варианты (превью) → реализовать изолированно →
тест всего пути → прогон вживую → коммит.
