# Отозванный подарок отвечал новичку, что его уже забрали

Симптом: даритель отзывает невостребованную ссылку, новичок открывает её и
слышит «Этот подарок уже забрали». Неправда — его никто не забирал, ссылку
забрали обратно. Человек идёт выяснять к другу, который знает, что не дарил
никому другому.

Причина оказалась не там, где я её уже чинил. Разводя причины отказа по
входу в бота (`link_gift_on_start`), я аккуратно отделил `REVOKED` от
`ALREADY_REDEEMED`. Но у подарка два места проверки: вход по ссылке и
активация в конце онбординга (`redeem_gift`). Во втором остался прежний
свалочный код:

```python
if gift.status is not GiftStatus.ISSUED:
    return GiftRefusal.ALREADY_REDEEMED
```

Пока отзывать было нечем, разница не проявлялась: до `REVOKED` статус просто
не доходил. Отзыв появился на шаг позже — и старая ветка начала врать.

## Как починили

Отделили `REVOKED` и в `redeem_gift`, до общей проверки «не ISSUED»:

```python
if gift.status is GiftStatus.REVOKED:
    return GiftRefusal.REVOKED
if gift.status is not GiftStatus.ISSUED:
    return GiftRefusal.ALREADY_REDEEMED
```

Поймал это не человек, а тест `test_revoked_link_stops_working`, написанный
вместе с самим отзывом: он проверял ровно то, что отозванная ссылка
перестаёт работать **и говорит правду о причине**.

## Урок

Новое значение статуса — это не одно место в коде. Прежде чем добавлять его,
найти все ветки, где статус сравнивается через `is not <нормальное значение>`:
каждая такая проверка молча зачислит новичка в чужую категорию.

Тот же приём с тем же следом: проверка «всё ли перечислено» окупается, когда
значений станет больше. У текстов отказов такая проверка есть отдельным
тестом — новая причина без текста уронила бы `KeyError` в лицо человеку.
