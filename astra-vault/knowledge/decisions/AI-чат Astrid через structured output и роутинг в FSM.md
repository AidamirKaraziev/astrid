# AI-чат Astrid: свободный текст вместо кнопок

> **Статус 2026-08-07.** Код в `src/astra/telegram/ai_chat/` живёт на `main`
> (ветка `feature/ai-chat-astrid` слита и удалена), но флаг
> `ai_chat_enabled` в `core/config.py` по умолчанию `False` — в проде раздел
> не включён. Этапы 1–5 ниже не сделаны.

## Идея

Пользователь пишет Astrid обычным текстом («хочу проверить совместимость с
парнем, он Овен, родился 3 марта 92-го в Алматы»), а бот сам вытаскивает
структуру и запускает нужный продукт. Кнопки остаются — AI-чат их дополняет,
а не заменяет.

## Ключевое архитектурное решение

**LLM не хранит состояние и ничего не делает сам.** Он только превращает
болтовню в структуру (slot filling) через structured output и говорит, куда
роутить. Истина о состоянии — в нашем FSM + БД, как и раньше.

Это ложится ровно на существующую архитектуру Astra:
- LLM-слой уже есть (`llm/factory.py`, DeepSeek, `json_mode`).
- FSM-флоу уже есть (`states.py`, `handlers/*`).
- Pydantic-схемы уже есть → это готовые «инструменты» для LLM.

Прототип НЕ переписывает хендлеры — он оборачивает вход и роутит в них кнопкой.

## Компоненты прототипа (`src/astra/telegram/ai_chat/`)

| Файл | Роль |
|---|---|
| `intents.py` | Pydantic-схемы: `Intent`, `BirthData`, `AstridReply` — «инструменты» |
| `prompt.py` | Системный промпт: персона + каталог продуктов + схема ответа |
| `agent.py` | Обёртка над `get_llm_provider`, вызов с `json_mode`, парсинг в `AstridReply` |
| `handler.py` | aiogram-роутер: ловит текст вне FSM, ведёт диалог, роутит кнопкой |

Флаги: `ai_chat_enabled` (по умолч. False), `ai_chat_provider` (deepseek).
Роутер регистрируется **последним** → кнопки и активные FSM ловятся раньше, конфликтов нет.

## Как это работает (один ход)

```
текст → run_astrid(history, text) → LLM (json_mode) → AstridReply
  ├─ reply           → отправляем пользователю
  ├─ birth_data      → накопленный slot filling
  ├─ missing         → чего не хватает (спросит следующим ходом)
  └─ ready_to_route  → показываем кнопку перехода в реальный флоу
```

История диалога живёт в FSM-хранилище (Redis) — `state` как память разговора.

## План внедрения (поэтапно)

**Этап 0 — прототип (сделано, эта ветка).** Диалог + slot filling + распознавание
намерения + кнопка перехода. Работает на текущем DeepSeek без новых зависимостей.

**Этап 1 — сквозной роутинг данных.** Сейчас кнопка ведёт в начало FSM-флоу.
Прокинуть уже собранные `birth_data` в стейт совместимости/натала, чтобы флоу
стартовал с предзаполненными полями (не переспрашивал то, что Astrid уже поняла).
Нужны entry-points в `handlers/compatibility.py` и `natal.py`, принимающие
частичный `BirthData`.

**Этап 2 — резолв города.** `birth_city` (строка) → реальный `Place` через
существующий `places/getters`. При неоднозначности («Ростов») — показать выбор
кнопками (переиспользовать `keyboards_places`).

**Этап 3 — валидация и безопасность.** Клэмп дат/времени (`utils.parse_birth_date`),
защита от prompt injection, лимит длины, антиспам. Фолбэк при фейле LLM (уже есть).

**Этап 4 — нативный tool-calling.** Сейчас structured output через JSON. DeepSeek
OpenAI-совместим → можно перейти на настоящие `tools`/`function_call` для более
надёжного роутинга и мультишаговых действий. Расширить `CompletionRequest` полем `tools`.

**Этап 5 — вход и метрики.** Кнопка «💬 Спросить Astrid» в главном меню, онбординг
через чат для новых пользователей, аналитика: доля дошедших до продукта через чат
vs кнопки, % успешного slot filling.

## Риски и как сняты

- **Конфликт с FSM** → роутер последний + `StateFilter(None)`.
- **Галлюцинация данных** → правило «не уверен — null», валидация нашими utils.
- **Фейл LLM** → `_fallback()`, диалог не падает.
- **Стоимость** → DeepSeek дёшев; `thinking_disabled`, лимит истории 12 реплик.
