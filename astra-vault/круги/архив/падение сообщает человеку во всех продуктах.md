# Падение сообщает человеку во всех продуктах

Цель: ни один продукт не отвечает человеку тишиной, когда у него что-то
упало; параллельные прогоны тестов перестают вычищать друг друга.

Готово, когда: уведомление о сбое совместимости и натала приходит из одной
точки на продукт и покрывает все пути падения; `uv run pytest -q` зелёный;
два одновременных полных прогона в разных дорожках не роняют друг друга.

## Что сломано (проверено, не предположение)

### Совместимость молчит на пяти путях из шести

`mark_report_failed` в `compatibility_service.py` вызывается шесть раз:

| строка | причина | человек узнаёт |
|---|---|---|
| 340 | `deepseek_disabled` | нет |
| 352 | `llm_failed` | **да** |
| 365 | `except` после LLM | нет |
| 381 | `missing_llm_output` | нет |
| 400 | `except` на сборке PDF | нет |
| 599 | `pdf_missing` | нет |

Это тот же режим отказа, что скрывал баг натальной карты: в базе `failed`,
человеку — ничего.

### Эталон уже есть в этом же проекте

Таро и «Спроси Астрид» сделаны правильно: уведомление стоит **в вызывающем
воркере**, на `reading is None` (`workers/handlers.py:396` и `:446`), и
покрывает любой путь падения внутри сервиса. У совместимости такие точки
вызова тоже есть — `handlers.py:248` и `:273`, — и они уже проверяют
`report is None`, но только пишут в лог `ABANDONED`.

### Денежного бага нет

Проверено по схеме: колонок оплаты у `natal_reports` и
`compatibility_reports` нет вообще — продукты бесплатные. Возврат звёзд
есть только у таро и «Спроси», и он на месте. Строка в админке «Этот
продукт бесплатный — возвращать нечего» соответствует действительности, а
не является недоработкой.

### Параллельные дорожки вычищают друг друга

`purge_test_users` в `tests/conftest.py` удаляет **всех** пользователей в
тестовом диапазоне `telegram_id` (9·10⁹…9.999·10⁹) до и после каждого
теста. Два прогона на общей базе `:15444` — и чистка одного сносит
пользователей другого на середине теста; профиль остаётся без владельца,
получается `ForeignKeyViolation on profiles` в
`tests/test_registration_funnel_e2e.py`. Два работника независимо на это
наткнулись, оба решили, что дело не в их правках, и были правы.

## Решено до старта

- Уведомление ставим в точку вызова, как у таро, а не внутрь сервиса.
  Причина структурная: любой новый путь падения внутри сервиса
  автоматически оказывается покрыт, и забыть его нельзя.
- Из `compatibility_service.py` внутреннее уведомление при этом **убираем**,
  иначе человек получит два сообщения на один сбой.
- Натал приводим к той же точке вызова и убираем разложенный по трём путям
  хелпер, добавленный в прошлом круге. Это переделка моей же свежей работы,
  и делается она не ради красоты: два разных способа решать одну задачу в
  одной кодовой базе — это ровно та неоднородность, из которой и выросли
  оба найденных бага.
- Тексты уведомлений не меняем: берём существующие `NATAL_FAILURE_TEXT` и
  `COMPATIBILITY_FAILURE_TEXT`. Тексты бота правятся по канону и отдельно.
- Диапазон тестовых `telegram_id` делим между прогонами, а не заводим базу
  на дорожку: своя база потребовала бы миграций на каждый прогон и
  переписывания `make infra`. Делёж диапазона — правка одного файла.

## Не трогаем

`services/natal_failure_notify.py` и `services/compatibility_failure_notify.py`
не правим: они исправны, и их текст — канон. Возвраты звёзд не трогаем
вовсе: у бесплатных продуктов их нет по решению, а у платных они работают.

## Задачи

### Совместимость и натал сообщают о сбое из одной точки
кому: работник бэк · файлы: src/astra/workers/handlers.py, src/astra/services/compatibility_service.py, src/astra/services/natal_report_service.py, tests/test_failure_notifications.py
готово, когда: на каждый продукт одна точка уведомления в `handlers.py`; внутренние вызовы уведомлений из обоих сервисов убраны, двойных сообщений нет; новый тест проверяет, что сбой на любом пути (у совместимости все шесть, у натала все три) доводит до человека ровно одно сообщение
проверка: uv run pytest -q tests/test_failure_notifications.py

### Параллельные прогоны не вычищают друг друга
кому: работник бэк · файлы: tests/conftest.py
готово, когда: каждый прогон работает в своём поддиапазоне тестовых `telegram_id` и чистит только его; два одновременных полных прогона на одной базе проходят оба
проверка: два одновременных `uv run pytest -q tests/test_registration_funnel_e2e.py` на общей базе — оба зелёные

```
     задача                             время  токены  окно  проверка

  ✓  Диапазоны тестовых id               0.1 ч   110k   11%  две пары зелёных
                                        ─────  ──────
                                         0.1 ч   248k
```

Проверено на объединении, не по отчётам:

- `make lint` → `ruff: All checks passed`, `mypy: Success`
- `uv run pytest -q` → `1442 passed` (было 1426; +16 тестов)
- контроль на двойное сообщение: вернул внутреннее уведомление в сервис
  совместимости → тест упал на `llm_none-generate`. Работник этот контроль
  не прогонял и честно об этом написал; прогнал я
- контроль гонки: два одновременных прогона
  `tests/test_registration_funnel_e2e.py` → оба `29 passed`

### Путей оказалось больше, чем в задании

Я написал «у натала три пути», работник нашёл **пять**: `deepseek_disabled`
и `missing_llm_output` тоже были немыми, я их пропустил при разборе. Он
покрыл все пять и назвал расхождение в отчёте, вместо того чтобы молча
сделать по заданию. Итого закрыто одиннадцать немых путей: шесть у
совместимости, пять у натала.

### Долг, оставленный осознанно

- Вторая гонка параллельных прогонов (`tests/fake_telegram.py` начинает id
  сообщений с 1000, а `support_tickets` уникальна по
  `admin_chat_id + admin_message_id`) обойдена **фикстурой в `conftest.py`,
  которая оборачивает `FakeTelegramSession.__init__`**. Работник не стал
  править чужой файл и прямо сказал, что правка самого `fake_telegram.py`
  была бы чище. Согласен: обёртка — заплатка.
- Делёж слотов держится файловой блокировкой в системном `tmp`, то есть
  работает между процессами одной машины. Если базу начнут делить разные
  машины, понадобится другой способ.
- Повторная доставка PDF совместимости из бота
  (`telegram/handlers/compatibility.py:765`, `resend=True`) идёт мимо
  воркера: если там PDF пропал, человек общего уведомления не получит.
  Единственный известный путь, не сведённый к точке вызова.
